Deploying the service

We deploy the service several times a day, and every deploy goes through the same pipeline: build, test, stage, canary, then full rollout. The goal is to make the safe path the easy path so nobody is tempted to skip a step when they are in a hurry.

The canary stage watches error rates, latency, and a few business metrics for ten minutes. If any of them drift outside the expected range, the deploy is rolled back automatically and the on-call engineer gets a page with the comparison.

After the canary passes, the deploy moves to the full fleet in batches. Each batch waits for the previous one to report healthy, so a bad build never reaches every user at once. The release notes are generated from the commit log and linked from the deploy page.

Rollbacks are boring on purpose. The previous build is still available, the database migrations are backward compatible for at least one release, and the feature flags let us turn off a new path without shipping code. That combination is what makes deploying on a Friday afternoon uneventful.
